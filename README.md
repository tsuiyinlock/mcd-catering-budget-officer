## 这个项目解决什么问题

行政部门每月都要给团队订麦当劳午餐。听起来简单，实际要处理：

- 20 人份点单，手算总价半小时，还经常算错
- 门店有满 300 打 7.8 折、满 1000 打 7 折等阶梯，但**规则是结构化原始数据**，得自己解读
- 要凑单到门槛才划算，到底该点多少
- 20 份同款巨无霸，配出去很难看

**团餐预算官**把这件事自动化：输入人数、预算、时间、地址，输出一份含优惠核算的完整配餐清单。

## 核心能力

### 1. 配餐预算求解器

不是简单的「推荐一个套餐」，而是一个可验证的求解过程：

- **官方档位规则** —— 人均 <20 / 20-30 / 30-40 / 40-50 / ≥50 元，各档对应不同的套餐结构（规则来源为 `query-meals` 官方描述）
- **主餐轮换** —— 20 人自动分配到不同汉堡，不会全是同款
- **小食均衡** —— 按累计使用次数最少优先轮转
- **满减凑单** —— 主动计算距离下一档门槛的差额，并判断「再花 X 元净省 Y 元」是否成立
- **档位保护** —— 预算不足时优先保住主餐，绝不静默地退化成纯小食；实在配不上会明确告诉你人均该加多少

### 2. 真实接口结构驱动的优惠计算

促销规则不是简单的「满 X 减 Y」，实测返回的结构有四个坑，本项目逐一处理：

| 坑 | 真实情况 | 本项目处理 |
|---|---|---|
| 折扣语义 | `discount: "30"` = 减免 30% = **7 折**，不是 3 折 | 按减免百分比换算 |
| 单位混用 | 门槛是**元**，而 `calculate-price` 价格是**分** | 全程转「分」计算 |
| 服务绑定 | 每条规则绑定 `gmServiceCode`，折扣不同 | 按助餐服务过滤规则 |
| 规则形态 | 实测几乎全是**满折**，满减需按阶梯处理 | 同时支持两种分支 |

第 3 点尤其重要：实测同一门店 GMS001 满 1000 打 7 折，而 GMS003 满 1000 仅打 8.5 折。
不做过滤就会承诺一个根本拿不到的优惠 —— **这在企业报销场景里是会出事的**。

### 3. 助餐服务可用性判断

实测 `query-meal-assistance` 会返回不可用原因：

| 服务 | 内容 | 实测状态 |
|---|---|---|
| GMS001 保鲜速达 | 准时送达 & 餐品保温 | 全天可用 |
| GMS002 专人分餐 | 送餐到桌/到人 | 仅 07:00~20:00 |
| GMS003 专人摆台 | 餐品摆台、专人服务 | 仅 07:00~20:00 |

深夜下单时只有 GMS001 可选。Skill 会读取 `unusableReason` 展示真实可选范围，而不是硬编码推荐。

### 4. 全流程工具编排

```
配送地址 → 团餐门店 → 助餐服务 → 促销规则 → 在售餐品
    → 配餐求解 → 计价核对 → （用户确认后）下单
```

所有 `addressId` / `storeCode` / `beCode` 均来自上游接口返回值，**不做任何臆测或构造**。

### 5. 金额单位严格管控

MCP 返回的价格单位是**分**。项目内部全程使用「分」计算，仅在渲染时转「元」。这是企业场景下最容易出错、也最容易被财务审计抓住的地方。

## 快速开始

### 环境要求

- Node.js ≥ 18（仅用于运行配餐求解器，无第三方依赖）
- 一个有效的麦当劳 MCP Token

### 1. 配置 MCP

将以下内容加入你的 MCP 配置，把 `${MCP_TOKEN}` 替换为实际 Token：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer ${MCP_TOKEN}"
      }
    }
  }
}
```

### 2. 安装 Skill

把 [`SKILL.md`](./SKILL.md) 与 [`scripts/`](./scripts) 目录放入你的 Skill 工作目录。

### 3. 验证求解器

```bash
node scripts/plan-catering.js
```

会依次求解 4 个典型场景（20 人团餐、12 人紧预算、35 人大团餐、8 人下午茶）并输出完整方案。

### 独立调用求解器

促销规则按 `query-promotions` 的**真实返回结构**传入（含 `ruleDetail` 与 `gmServiceCode`）：

```js
const { planCatering, formatPlan, toCalculatePriceItems } = require('./scripts/plan-catering.js');

const plan = planCatering({
  headcount: 35,
  budgetTotalFen: 157500,          // 1575 元，单位：分
  menu: [
    { productCode: 'B01', name: '巨无霸汉堡', priceFen: 2200, categoryRaw: '汉堡' },
    { productCode: 'S01', name: '中薯条',      priceFen: 800,  categoryRaw: '小食' },
    { productCode: 'D01', name: '中可乐',      priceFen: 700,  categoryRaw: '饮料' },
  ],
  // 来自 query-promotions，原样传入即可，求解器会处理单位与折扣语义
  promotions: [
    {
      promotionId: '331878002',
      promotionType: '33',
      ruleCategory: 30,
      gmServiceCode: 'GMS001',
      products: [{ type: '2', productCode: '9900016058' }],
      ruleDetail: { orderDiscount: { discount: '30', startDiscountPoint: '1000' } },
    },
  ],
  gmServiceCode: 'GMS001',        // 必传：决定适用哪些规则
});

console.log(formatPlan(plan));
const orderItems = toCalculatePriceItems(plan);  // 直接喂给 calculate-price
```

输出示例（35 人，原价 ¥1285.00，命中满 1000 打 7 折）：

```
原价合计：¥1285.00
  适用优惠：满 1000.00 打 7 折
优惠减免：-¥385.50
到手合计：¥899.50
人均：¥25.70（预算 ¥45.00/人）
✓ 结余 ¥675.50
```

### 边界情况处理

| 情况 | 处理方式 |
|---|---|
| 预算不足以覆盖主餐 | 明确告知「人均 ¥18 不足一份麦辣鸡腿汉堡（¥19）」，并建议人均加 ¥1 或人数减至 7 人 |
| 距离满折门槛还差一点 | 提示「再点 ¥56.00 可触发满 300 打 7.8 折，净省 ¥10.00」 |
| 已命中的规则不再重复提示 | 门槛按**原价**判定，已享受的规则不会再次出现在凑单建议里 |
| 深夜 / 非营业时段 | `query-meals` 返回 `600057`，读取 `reservationTimeOptions` 告知可预约时段后重试 |
| 助餐服务不可用 | 读取 `unusableReason`（实测如「专人服务仅对送达时间为 07:00~20:00 点的订单可享」） |
| 菜单无主餐类餐品 | 降级为纯小食组合，并给出警告 |
| 全部方案超预算 | 取最低价方案并显式警告，不静默通过 |

## 常见问题

**Q：为什么不用现成的省钱 Skill？**
A：省钱类项目面向个人零售（`beType=1/2/5`），拿不到团餐专用的促销规则接口。团餐的满减逻辑、门店助餐服务、配送能力都与零售不同。

**Q：为什么价格单位要全程用「分」？**
A：MCP 接口返回单位是分。企业订餐金额动辄上千，任何一次单位混淆都会造成对账事故。全程用分、末端转换是最稳妥的做法。

**Q：会替我自动下单吗？**
A：不会。`create-order` 只在你明确确认后执行，且下单前会完整展示门店、时间、清单、优惠明细和实付金额。

**Q：优惠规则能叠加吗？**
A：不能假设能。工具不保证规则之间可叠加，因此求解器采取「取最优单条」策略，避免承诺无法兑现的金额。
